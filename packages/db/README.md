# DentalOS Database

This package owns the DentalOS PostgreSQL data model and Prisma client boundary.

## Phase 2 scope

The schema covers the core SaaS domains defined by the project requirements:

- tenants and branches
- users, Better Auth core tables, memberships and branch access
- patients and patient portal linkage
- appointments, status history and reminders
- treatment records and amendment history
- treatment plans and planned treatments
- prescriptions, medication entries, versions, status history and refill requests
- patient documents and prescription PDF metadata
- in-app notifications
- audit logs
- configurable dashboard templates and per-device layouts
- SaaS billing plans, subscriptions, invoices and payments

## Tenant isolation

Tenant-owned operational records carry `tenantId` and branch-owned records also carry `branchId`. Application authorization must always validate both the authenticated membership and the requested tenant/branch scope. A clinic subdomain is only a routing mechanism; it is not an authorization boundary.

## Identity numbers

Internal database IDs use opaque CUIDs. Business identifiers are separate:

- Patient: `patientNumber` — generated as an 8-digit random identifier.
- Appointment: `appointmentNumber` — generated by the application using `DDMMYY-BR##-###` with a branch/date sequence.

Generation must happen transactionally so concurrent requests cannot create duplicate business identifiers.

## Clinical history

Treatment records are intentionally non-destructive. Corrections create an amendment linked to the original record. Prescription edits use immutable version snapshots. Appointment, treatment-plan and prescription status changes have history tables.

## Documents

`Document` stores Supabase Storage metadata, not public URLs. Patient/clinical document authorization must be enforced by the API before generating signed download URLs. Prescription PDF regeneration is represented with document versions and `isLatest`/archive state.

## Important implementation note

The Prisma schema is the Phase 2 architecture baseline. Do not treat the presence of a field as permission to expose it to every role. Authorization, tenant isolation and branch visibility remain application/service-layer responsibilities.

No migration was fabricated in GitHub. After dependencies are installed locally and Supabase credentials are configured, run:

```bash
pnpm --filter @dentalos/db prisma:format
pnpm --filter @dentalos/db prisma:validate
pnpm --filter @dentalos/db prisma:generate
pnpm --filter @dentalos/db prisma:migrate
```

The first migration should be generated against the actual development database rather than committed as hand-written SQL.
